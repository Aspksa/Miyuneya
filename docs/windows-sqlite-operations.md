# Эксплуатация Miyuneya: Windows, SQLite, обновления и большой архив

Реализованы выбранные направления №9, 10, 12, 15, 17–22, 24. Меню «Мозги Hayumeri» и страница `/workspace` не изменены.

## Портативный Windows-запуск

Дважды нажмите `Miyuneya.bat`. PowerShell 5.1 сначала проверит портативный Node.js 22.18+; если он отсутствует и есть подключение к сети, загрузит официальный Node.js с nodejs.org и сверит закреплённую SHA-256. После первого успешного запуска следующая загрузка возможна без интернета. Требования к системному Python нет, права администратора не нужны. Для полностью офлайн-первого запуска заранее положите совместимый `node.exe` в `.runtime/node/node.exe` либо задайте `MIYUNEYA_NODE`.

Сценарии GitHub CI проверяют: официальный первый запуск и повторный офлайн; недействительную контрольную сумму; OneDrive-подобный путь с пробелами, знаками `&`, `%` и кириллицей; запуск без установленного Python, восстановление чата после перезапуска, работу без прав администратора. На конкретном ноутбуке и M.2 SSD условия могут отличаться — пользовательская проверка на своём оборудовании остаётся необходимой.

## Отказ питания и одновременные операции

SQLite использует WAL и `synchronous=FULL` и проверяет версионность сообщений. При аварийном завершении процесса повторный запуск восстанавливает уже зафиксированные транзакции, но запись, для которой приложение не получило подтверждение COMMIT, не считается сохранённой. Нельзя вручную удалять живые файлы `archive.sqlite-wal` или `-shm`. Тесты проверяют завершение процесса и повторное открытие базы.

Во время JSONL-импорта совместное соединение не допускает параллельных транзакций. Поиск использует отдельный Worker; резервирование выполняется через официальный SQLite Backup API. Добавлены сценарии одновременного поиска, новых сообщений и создания копии, а также полный откат импорта при конфликте.

## Переход к старому сообщению

Откройте историю в плавающем чате. В поле поиска выберите режим, затем нажмите «К найденному сообщению» возле результата. Поиск возвращает ID именно того сообщения, которое сформировало фрагмент совпадения. Альтернатива — выбрать дату и нажать «К дате»: чат откроет первую запись начиная с 00:00 UTC указанного дня, если она существует. Для вложенных веток используются видимые части родительской истории, а не вся исходная ветка. Данные загружаются страницей в 100 сообщений с небольшим контекстом вокруг найденного.

## Фоновое обслуживание

В существующих настройках чата выберите интервал планировщика **15, 30 или 60 минут** (по умолчанию 30). Первое обслуживание планируется через 12 секунд после запуска, последующие — по выбранному интервалу, **только пока Miyuneya запущена**. Планировщик не запускает новую работу поверх уже выполняющегося задания и пропускает обслуживание во время импорта.

- Глубокая проверка индексов, веток, внешних ключей и вложений — не чаще одного раза в сутки.
- Обновление статистики планировщика `PRAGMA optimize` — после успешной суточной проверки.
- Резервная копия — не чаще одного раза в 24 часа, с дополнительной копией на внешний SSD при настройке.
- Проверка размера WAL — при каждом цикле обслуживания. При достижении 32 МиБ выполняется только `wal_checkpoint(PASSIVE)` в отдельном Worker. При размере 256 МиБ и выше или занятости WAL появляется предупреждение. Нельзя принудительно обрезать WAL при активных читателях.

Журнал `data/chat-backups/maintenance-events.jsonl` хранит только время, наименование операции, статус, код и длительность. **Никаких текстов сообщений, SQL-запросов, путей или секретных ключей**. Размер ограничен ротацией файлов примерно по 512 КиБ. Последние события доступны по кнопке «Журнал обслуживания». Это журнал событий, а не механизм гарантированного хранения данных.

## Проверка после установки обновления

Ранее успешный HTTP-запуск ещё не гарантировал исправность SQLite. Теперь после применения подготовленного релиза и запуска сервера, **до подтверждения обновления**, стартер через защищённый служебный запрос проверяет:
1. Совместимость версии схемы SQLite v4 и наличие основных таблиц.
2. `PRAGMA quick_check`, `foreign_key_check` и целостность FTS5.
3. Корректное завершение защищённого запроса на сервере.

Если хотя бы один пункт не пройден, кандидат прекращает работу, существующий механизм восстановления откатывает изменённые файлы и пытается запустить прежнюю версию. Пользовательские директории `data/`, `vault` и настройки Cloud.ru не обновляются этим механизмом. Разрешённый список обновлений включает только конкретные модули чата/поиска и файлы оформления, но не разрешает запись пользовательских данных.

Отдельный тест создаёт намеренно неработающий SQLite preflight в подготовленном обновлении и проверяет восстановление прежнего файла.

## Измеряемая производительность

Для тестов создаётся **отдельная временная база**, а не реальная `data/chats/archive.sqlite`.

```powershell
node scripts/benchmark-chats.mjs --messages=10000
node scripts/benchmark-chats.mjs --messages=100000 --confirm-large
node scripts/benchmark-chats.mjs --messages=1000000 --confirm-large
```

Результат — фактическое число записей в секунду, время поиска, страниц, размер БД и RSS-память. После окончания тестовый архив удаляется. Прогон на 100 тыс. или миллион **может быть очень продолжительным и создавать нагрузку на SSD**; это ручные тесты, они не выполняются при обычном старте или каждом CI. Небольшой тестовый прогон проверяет работоспособность самого измерителя в CI.

## Границы и безопасность

Стабильность не доказывается одним CI на GitHub: система файлов и реальный внешний M.2 могут вести себя иначе. Не удаляйте рабочие SQLite-файлы, не пытайтесь восстановить отдельные файлы резервной копии поверх работающего процесса и держите независимую проверенную копию на другом физическом носителе. Автоматическое восстановление всего архива одной кнопкой, шифрование базы и политика удаления старых поколений сюда не входят.
