# Запуск Miyuneya в Windows

## Единственная основная цепочка

`Miyuneya.bat` → `scripts/bootstrap.ps1` → `scripts/start.mjs` → `scripts/serve.mjs` → `server/app.ts`.

BAT: ASCII без BOM, CRLF, `DisableDelayedExpansion`. Все пути заключены в кавычки; `%*` не исполняется. BAT не зависит от cwd и не передаёт пользовательский текст в CMD. PowerShell вызывается по системному пути, без профиля; `ExecutionPolicy Bypass` действует только на этот процесс, а не меняет настройки Windows.

PowerShell проверяет `MIYUNEYA_NODE`, затем `.runtime/node/node.exe`, подготовленный версионный Node и найденные через PATH экземпляры. Проба реально исполняет JS, загружает `node:http`, `node:crypto`, `node:module` и удаляет типы TypeScript. Проба ограничена временем. Если явный `MIYUNEYA_NODE` неверен, требуется исправить эту настройку. Повреждённые автоматические кандидаты пропускаются.

При необходимости скачивается только официальный `node.exe` с `nodejs.org`, версия и SHA-256 закреплены в `scripts/runtime-sources.json`. SHA считается средствами .NET, чтобы не зависеть от доступности функции `Get-FileHash` в PowerShell, запущенном из Node/PowerShell 7. Новая версия сначала загружается во временную папку, сверяется по SHA и реально запускается; только затем устанавливается под mutex. Ранее подготовленные файлы не удаляются при неудаче проверки.

Node-лаунчер использует `process.execPath` для своих дочерних процессов. В Windows единственный экземпляр охраняет именованный канал ОС: нет убийства чужого PID и старого PID-файла, блокирующего запуск. Linux использует отдельную реализацию той же блокировки с идентичностью процесса из `/proc`; в ограниченных средах без `/proc` доступна проверка живого PID. macOS не является проверяемой платформой этой версии.

`web/` — исходные HTML/CSS/SVG, `src/` — TypeScript, `dist/` — готовые файлы и манифест SHA. Сборка пропускается только после проверки всех обязательных файлов. В Git для исходников и выходных файлов закреплён LF, для BAT — CRLF: смена платформы не создаёт ложную неисправность сборки. Компиляция не требует внешних зависимостей.

Сервер выбирает свободный порт через `listen(0)`. После запуска родитель проверяет HTTP 200, `app`, идентификатор копии, одноразовый идентификатор запуска и `ready=true`, затем все обязательные ресурсы. Только после этого публикуется адрес экземпляра и открывается браузер. Проверки localhost используют `node:http` напрямую и не зависят от HTTP-прокси для внешнего интернета.

## Сохранение и очистка

Сервер пишет JSON через временный файл в той же папке, `fsync`, закрытие дескриптора и атомарный rename. Во время штатного завершения он прекращает приём новых запросов, дожидается текущих обработчиков и очереди записи; лаунчер ждёт закрытия дочернего процесса и лишь затем освобождает блокировку и удаляет указатель сеанса.

Для временных блокировок `EBUSY`, `EPERM`, `EACCES`, `ENOTEMPTY` есть ограниченные повторы. Постоянная ошибка видима. Таймаут штатного завершения не является ожиданием «на глаз»: это предел ожидания реально завершающегося дочернего процесса; принудительно завершается только собственный дочерний процесс.

Тесты используют общий помощник `tests/helpers/lifecycle.mjs`: сначала останавливаются принадлежащие тесту процессы/серверы, затем удаляется папка. Проблемы очистки не подавляются.

## Локальный пакет обновления

```json
{
  "schema": 1,
  "version": "0.2.1",
  "files": [
    { "path": "web/style.css", "sha256": "64 строчных шестнадцатеричных символа SHA-256" }
  ]
}
```

Фактический манифест должен содержать настоящий хеш, а не приведённое описание. Файлы лежат относительно папки пакета. Разрешены `src/<имя>.ts`, `server/app.ts`, четыре исходных ресурса `web/index.html`, `web/style.css`, `web/fox.svg`, `web/favicon.svg`. Запрещены повторяющиеся пути, traversal, symlink и замена пользовательских данных. Это не общий установщик произвольных ZIP: BAT/лаунчер/пакеты и схема данных не обновляются этим механизмом.

Резервирование завершается до записи журнала и изменения кода. Журнал позволяет повторять откат после прерванного восстановления. Установка фиксируется только после запуска нового серверного процесса, правильного health-ответа и доступности ресурсов. Неудачная версия перемещается из активной очереди; следующий запуск не повторяет её автоматически.

## Что проверяется

Локальный Linux-прогон: UTC и Asia/Vladivostok, сохранность JSON и конфликты версий, кириллица и специальные символы, другой cwd, неверный health, занятый чужой порт, параллельный запуск, восстановление сборки, ожидание незавершённого PUT, повторы очистки, карантин и откат.

Windows CI запускает те же сценарии на настоящей Windows Server 2025, Node 22.18 и PowerShell 5.1. Дополнительно выполняются BAT через CMD, запуск по ассоциации файлов через ShellExecute, повреждённый portable Node, отсутствие Node при запрете интернета, повреждённый явный путь и неиспользуемый Python. Отдельная задача проверяет официальную загрузку Node, правильную и неправильную SHA-256 и автономный повтор. Результаты конкретного прогона доступны в PR.

Нажатие мышью в Проводнике на пользовательской Windows 10, открытие её браузера по умолчанию, физический USB-диск, корпоративные ограничения, ARM64 и UNC не подтверждены автоматизированными проверками. UNC намеренно отклоняется. ShellExecute проверяет ассоциацию BAT, но не заменяет ручную проверку интерфейса Проводника. Абсолютной гарантии отсутствия ошибок нет.

## Подтверждённый Windows-прогон

[GitHub Actions, прогон 40850976660](https://github.com/Aspksa/Miyuneya/actions/runs/40850976660) завершился успешно: Linux, Windows Server 2025 / Node 22.18 и отдельная установка Node 24.22.1. На Windows без пропусков прошли обе зоны UTC и Asia/Vladivostok, основной BAT через CMD и ShellExecute, кириллица и `! & ^ () % #`, пропуск повреждённого portable Node, явный неверный Node, отсутствие Node без сети, занятый чужой порт, восстановление сборки, параллельный запуск, ожидание записи и откат.

Отдельно подтверждены перенос папки с сохранённой заметкой с **D: на C:**, скачивание официального `node.exe`, проверка правильной SHA-256, отказ при неверной SHA-256 и повторный запуск с запретом загрузок. Проверка настоящего удерживаемого Windows-файла добавлена отдельным сценарием; её результат виден в последующем прогоне PR.

Это автоматические проверки в Windows CI, не ручной двойной щелчок на ноутбуке владельца. Открытие браузера при тестах отключено; проверена точка, в которой лаунчер считает сервер готовым, но не конкретная пользовательская ассоциация браузера.
